## 1. Approach

**Model:** Groq `qwen/qwen3.8-27b`, the only vision model on Groq's public list (a *preview* model). I originally planned Gemini and switched to Groq at the owner's request. Groq doesn't accept PDFs, so each PDF page is rendered to a PNG (pypdfium2, 150 dpi) and up to 3 page images go in one request.

**Why vision-first:** the sample pack mixes digital PDFs with scans and phone photos. A text-extraction pipeline sees nothing on a scan. Sending page images handles both kinds with one code path and no OCR stage to maintain. The cost is more input tokens per page than text, quantified below.

**Prompting:**
- Schema-constrained JSON (`response_format: json_schema`, `strict: true`) at temperature 0.
- One instruction block with explicit field rules: seller not buyer, issue date not due date, day-first vs month-first by vendor country, line amount before tax, discounts negative, tax = sum of tax lines, `0` when none.
- No examples from the labelled set.
- Our own parsing and Pydantic validation run on every response. Then an arithmetic check: line items + tax must equal the total.
- On failure, **one repair retry** with the errors fed back. If it still fails, the result is kept and flagged `needs_review`.

**Conventions aligned to the sample pack:** the pack's README and `schema.json` specify that `tax_total` is `0` (not `null`) when no tax is shown, that line-item `description` and `amount` are always present, and that discount rows are negative line items. The prompt and schema follow these published conventions. This is aligned to the pack's stated rules, not tuned on its errors ([docs/data_notes.md](docs/data_notes.md)).

### What didn't work

**Text-only extraction.** Same model and same rules, but the input is the PDF's text layer (pdfplumber) instead of page images. On digital PDFs it was just as accurate at about half the cost. On every scan and photo it failed completely: with no text to read, the model (correctly) refused to invent data and called them non-invoices. A text-only pipeline would silently lose that whole class of document. A hybrid (text when a PDF has a text layer, images otherwise) would cut cost on digital PDFs with no loss on this sample. That's listed under future work, not built.

## 2. Matching rules

<!-- MATCHING_RULES -->
| Field | Rule |
|---|---|
| `is_invoice` | Exact boolean, scored over all labelled docs. |
| all other fields | Scored only where GT `is_invoice` is true. For GT non-invoices, a separate `non_invoice_nulls` check asks that every other field is null. |
| `vendor` | Lowercase, `&`→`and`, strip punctuation, drop legal suffixes (co, company, corp, corporation, gmbh, inc, limited, llc, llp, ltd, plc, private, pvt). Correct if equal, or rapidfuzz `token_set_ratio` ≥ 90. |
| `invoice_number` | Uppercase, drop non-alphanumerics, exact (leading zeros kept). |
| `invoice_date` | Both parsed as ISO dates and equal; a non-ISO prediction is wrong. |
| `currency` | Uppercase; symbols mapped (₹/Rs→INR, €→EUR, £→GBP, $→USD); exact. |
| `tax_total`, `total` | Coerced to float (commas and symbols stripped); correct if \|a−b\| ≤ 0.01. Null matches only null (so 0 vs null is wrong). |
| `line_items` | Correct only if the counts are equal and every GT row is matched one-to-one (Hungarian assignment). A row matches if description `token_set_ratio` ≥ 80, quantity is equal (null≡null), and amount is within 0.01. Item-level P/R/F1 is reported too. |
| doc exact match | All 8 fields correct. |
| null handling | GT null vs a value = `hallucinated`; GT value vs null = `missed`; both present but different = `wrong_value`. |
<!-- /MATCHING_RULES -->

### Prompt v2: one tuning round (optimistic)

**v2 was tuned on the same 10 labelled documents, so its score is optimistic.** It is not evidence of how the pipeline does on new invoices. Only one tuning round was done. Every v2 change targets a failure category found in section 4, and each one is general rather than specific to a document:

1. **Tax added up in code:** the model lists each printed tax line (`tax_lines`), and the code computes `tax_total`. The output schema is unchanged.
2. **Discount rule spelled out:** discount, rebate and credit rows are negative even if printed without a minus sign.
3. **Specific repair message:** "line items sum to X, tax lines sum to Y, gap Z", plus what to re-check.
4. **Totals tolerance:** tightened from 0.5% to 0.05% of the total. A validation change, so it affects flagging, not extraction.

**What changed in practice:** both tax errors from v1 (L02, L10) are gone. The model now copies each CGST/SGST line, and the addition happens in code. L07's discount row is still positive, even though v2's repair message spelled out the exact gap (twice the discount) and told the model to check discount signs. That's the one remaining error, and the review flag catches it. The obvious next fix (flip a discount row's sign in code when that exactly closes the gap) was **not** applied, because it would be a second tuning round on the same documents.

*Run note:* Groq's daily quota ran out mid-way through the first v2 eval. Six documents completed on the first day. The other four, plus L07, whose repair call had been cut off, were re-run the next day with the same code and prompt. The v2 table scores those combined outputs. No document in it is quota-truncated.

## 4. Failure analysis (prompt v1)

From `reports/failures.md` (`scripts/failure_analysis.py`). Categories are assigned by heuristics first. Two were then changed after looking at the documents (marked *manual*, with the evidence). The same analysis for v2 is in `reports/failures_v2.md`: one error left (L07, discount sign), caught by validation.

**Main finding:** none of the v1 errors were misreads of the page. On L02 and L10 both tax lines are clearly legible and the line items and total were read correctly. The model added the two tax lines wrong. On L07 it dropped a minus sign. These are reasoning and arithmetic errors, which is why the v2 fix moves the addition into code instead of asking for "better OCR".

#### Examples and evidence

##### TAX_INTERPRETATION
- **L02 · tax_total**: Photo prints CGST 1,764.90 and SGST 1,764.90 (sum 3,529.80), both clearly legible. Predicted 3,549.80: the line items and total were read correctly, so this is most likely an addition error when the model combined two tax lines, not a misread. (The heuristic alone would have said OCR_READ_ERROR.)
- **L10 · tax_total**: Scan prints CGST 9,844.80 and SGST 9,844.80 (sum 19,689.60), clearly legible. Predicted 18,689.60, exactly 1,000 short: again the components are readable and the line items and total are right, so most likely an addition error. (The heuristic alone would have said OCR_READ_ERROR.)

##### TOTALS_SEMANTICS
- **L07 · line_items**: row 'Returning client discount (10%)': GT amount -450.0, predicted 450.0 (sign flipped)

#### Did validation catch the errors?

- Field level: **2/3** wrong fields were in a doc where a validation check fired (so it was retried and/or flagged).
- Doc level: **2/3** docs with an error were caught (L07, L10); missed: L02.
- Why L02 slipped through: the error is 20.00, but the totals tolerance was max(1.00, 0.5% x 23139.80) = 115.70. The tolerance is too loose for large invoices.

#### Did the repair retry help?

| Doc | First-attempt errors | Fixed by retry? |
|---|---|---|
| L07 | TOTALS_MISMATCH: lines+tax=5284.13, total=4384.13 | no |
| L08 | SCHEMA_ERROR: <root>: Value error, is_invoice is false but these fields are not  | yes |
| L10 | TOTALS_MISMATCH: lines+tax=89009.60, total=90009.60 | no |

1/3 retries fixed the problem (SCHEMA_ERROR: 1/1 fixed; TOTALS_MISMATCH: 0/2 fixed).

#### Fix first (ranked by errors removed x ease)

| # | Fix | Category | Errors it targets | Ease (3 = easy) | Score |
|---|---|---|---|---|---|
| 1 | Ask the model for each tax line separately and add them up in code | TAX_INTERPRETATION | 2 | 2 | 4 |
| 2 | State the discount-sign rule more forcefully, and give the repair prompt the actual arithmetic | TOTALS_SEMANTICS | 1 | 3 | 3 |

1. **Ask the model for each tax line separately and add them up in code.** Extend the internal LLM schema with tax_lines: [{label, amount}]; set tax_total = sum(tax_lines) in code. The output schema is unchanged. Removes the model's arithmetic from the loop.
2. **State the discount-sign rule more forcefully, and give the repair prompt the actual arithmetic.** The v1 prompt already says discounts are negative, but the model still returned +450, and the generic repair message didn't fix it. Make the repair prompt say: lines sum to X, tax Y, total Z, gap D. Check signs of discount rows and re-add the tax lines.
3. **Tighten the totals tolerance** (validation, not extraction). Use e.g. max(1.00, 0.05% of total), so a 20-rupee error on a 23,000-rupee invoice gets flagged. It doesn't fix errors, but it raises validation recall.

Observed outside the labelled set (no GT, not counted above): U05 is a scan rotated 90°. Printed on the page (read manually): invoice number `LP-10932`, date 2026-10-21. The v1 model read every amount correctly but returned invoice number `LP-10` and date 2021-10-21. The totals check cannot catch header errors like this.

## 6. Human-review flag (bonus)

`needs_review` is rule-based on purpose (cheap, explainable). A doc is flagged when any validation problem remains after the repair retry (totals mismatch, missing total or vendor, 2+ of vendor/number/date/total missing) or when extraction failed. A model-reported confidence score is a possible future addition, not used here.

## 7. Limitations and honest notes

- **n = 10 labelled documents** (9 invoices, 1 non-invoice). One document is 10 points of `is_invoice` accuracy and about 11 points on every other field. Treat all rates as indicative.
- **v2 is tuned on the eval set.** The v1 number is the headline. v2 is reported for transparency only.
- **Failure categories are partly manual.** Two of the v1 categories were changed after viewing the page images (evidence in section 4).
- **Convention alignment:** the `tax_total = 0` rule, non-null line amounts and negative discounts follow the pack's published labelling conventions.
- **The totals check can't see header errors.** On unlabelled U05 (a scan rotated 90°) both v1 and v2 read every amount correctly but misread the invoice number and year, so it wasn't flagged (details at the end of `reports/failures_v2.md`). Straightening rotated scans before sending them is the next fix for that category. It isn't covered by the labelled set, so it wasn't attempted in the single tuning round.
- **Not handled:** multi-invoice PDFs (one result per file), PDFs over 3 pages, handwritten invoices, password-protected PDFs (rejected), non-Latin scripts (untested).
- **Model availability:** `qwen/qwen3.8-27b` is a Groq preview model, and the free plan's daily quota limits throughput. Both are fine for this assignment but would need a paid tier or a production model in real use.
